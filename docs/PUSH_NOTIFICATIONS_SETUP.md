# Как включить пуш-уведомления

> **Статус на 06.09.2026: ключ создан и прописан на сервере, всё готово.**
> Ниже — что именно сделано и как это проверить; инструкция остаётся на
> случай, если ключ придётся выпускать заново.

Как это устроено: приложение забирает у системы токен устройства и
присылает его на сервер, сервер сам подписывает запрос и стучится в APNs.
Ключа не было до 06.09.2026 — всё это время `ApnsService` писал одно
предупреждение в лог при старте и молча ничего не отправлял, специально,
чтобы приложение работало и без ключа.

Вся процедура — примерно на 15 минут.

---

## Шаг 1. Создать ключ APNs в кабинете Apple

1. https://developer.apple.com/account → **Certificates, Identifiers & Profiles**.
2. Слева **Keys** → синий **＋**.
3. Key Name: `iWent APNs` (имя любое, оно только для вас).
4. Поставить галочку **Apple Push Notifications service (APNs)**. Рядом
   появится надпись «This service must have environment and type
   configured» и кнопка **Configure**. Нажать её и выбрать:
   - **Environment** → **Sandbox & Production**;
   - **Key Restriction** → **Team Scoped (All Topics)**.

   Пока не выбраны оба пункта, кнопка внизу остаётся серой.

   ⚠️ Apple предупреждает не зря: **эту конфигурацию нельзя изменить после
   сохранения.** Если выбрать только `Sandbox`, ключ навсегда останется
   тестовым и пуши из App Store через него не пойдут — придётся заводить
   новый. `Topic Specific` привязал бы ключ к одному bundle ID; ограничивать
   себя незачем.

   **Save** → **Continue** → **Register**.
5. **Download** — скачается файл `AuthKey_XXXXXXXXXX.p8`.
   **Скачать его можно один раз.** Сохраните в надёжное место (не в папку
   проекта — он не должен попасть в git).
6. Запомните **Key ID** — это те самые 10 символов `XXXXXXXXXX` из имени
   файла, они же показаны на странице ключа.

Team ID уже известен: **54NZBKX94C**. Bundle ID: **com.varyamalinina.iwent**.

Заодно проверьте, что у идентификатора приложения включён пуш:
**Identifiers** → `com.varyamalinina.iwent` → в списке capabilities
**Push Notifications** должен стоять галочкой. (Скорее всего уже стоит:
дистрибутивный профиль, который Xcode выпустил при первой отгрузке в
TestFlight, несёт `aps-environment: production`.)

## Шаг 2. Положить ключ на сервер

Один и тот же ключ работает и для sandbox, и для production — различает их
переменная `APNS_PRODUCTION`.

Заходим на машину и открываем `.env`:

```bash
ssh -i ~/.ssh/yandex-cloud ubuntu@213.165.213.224
```

```bash
nano /home/ubuntu/event_app_new/server/.env
```

В конец файла добавить пять строк:

```
APNS_KEY_ID=ZQ666P8WT8
APNS_TEAM_ID=54NZBKX94C
APNS_BUNDLE_ID=com.varyamalinina.iwent
APNS_KEY_P8="-----BEGIN PRIVATE KEY-----\nMIGTAgEA...\n...\n-----END PRIVATE KEY-----"
APNS_PRODUCTION=true
```

Про `APNS_KEY_P8` — единственное место, где легко ошибиться:

- содержимое `.p8` кладётся **в одну строку**, переносы заменяются на `\n`
  (два символа: обратный слэш и `n`), вся строка — в двойных кавычках;
- строки `-----BEGIN PRIVATE KEY-----` и `-----END PRIVATE KEY-----`
  обязательно остаются на месте.

Быстрый способ получить такую строку — на своём компьютере (не на сервере):

```bash
awk 'BEGIN{ORS="\\n"} {print}' ~/путь/к/AuthKey_XXXXXXXXXX.p8 | pbcopy
```

После этого содержимое уже в буфере обмена — останется вставить его между
кавычками.

Сохранить (Ctrl+O, Enter, Ctrl+X) и перезапустить сервер:

```bash
pm2 restart event-app-server && pm2 logs event-app-server --lines 40 --nostream
```

В логе **не должно** быть строки «APNs не настроен». Если она есть — сервер
не увидел какую-то из трёх обязательных переменных
(`APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_KEY_P8`).

## Проверка ключа без телефона

Полезно, когда пуши не идут и непонятно, в ключе дело или в токене. Запрос
с заведомо неверным токеном устройства:

- **`400 BadDeviceToken` — это хороший ответ.** Токен фальшивый, но ключ,
  Key ID, Team ID и topic Apple приняла.
- `403 InvalidProviderToken` — неверен сам ключ или Key ID / Team ID.
- `400 TopicDisallowed` — не тот bundle ID.

Проверено 06.09.2026 на обоих адресах: `400 BadDeviceToken`.

## Шаг 3. Проверить

1. Установить свежую сборку на телефон и войти в аккаунт. Разрешение на
   уведомления спрашивается **после входа** — системное окно должно
   появиться один раз.
2. Убедиться, что токен долетел:

```bash
ssh -i ~/.ssh/yandex-cloud ubuntu@213.165.213.224 \
  "sudo -u postgres psql -d event_app -c 'SELECT \"userId\", platform, \"updatedAt\" FROM \"PushToken\" ORDER BY \"updatedAt\" DESC LIMIT 5;'"
```

3. С другого аккаунта сделать что-нибудь, что рождает уведомление — заявку
   в друзья или заявку на участие. Пуш должен прийти на телефон, а в логе
   сервера не должно быть ошибок APNs.

## Sandbox и production — переключать больше не нужно

Токен устройства не говорит, из какой он среды, а среда берётся из профиля
подписи: сборка, поставленная из Xcode по кабелю, регистрируется в
**sandbox**, сборка из TestFlight или App Store — в **production**.

Раньше сервер знал ровно один адрес, и токен «не из той» среды получал
`400 BadDeviceToken`, после чего запись о нём **удалялась** — то есть
проверять пуши на кабельной сборке и одновременно слать их живым
пользователям было нельзя, и приходилось помнить про переключение флага.

Теперь сервер при `BadDeviceToken` повторяет запрос во вторую среду, а
запись удаляет, только если токен отвергнут везде. `APNS_PRODUCTION` теперь
задаёт лишь то, **какой адрес пробуется первым** — оставляйте `true`,
переключать ничего не надо.

Файл `ios/iwent/iwent.entitlements` при этом трогать **не надо**: там
намеренно стоит `aps-environment: development`. Xcode при отгрузке
подставляет production-профиль, и значение берётся из него, а не из файла.
Если поправить файл на `production`, сломаются локальные сборки на телефон.

## Где это в коде

| что | файл |
|---|---|
| запрос разрешения и отправка токена | `client/hooks/usePushNotifications.ts` |
| приём токена | `POST /users/me/push-token` (`server/src/users/users.controller.ts`) |
| подпись JWT и отправка в APNs | `server/src/notifications/apns.service.ts` |
| тексты пушей (ru/en) | `server/src/notifications/push-texts.ts` |
| единая точка отправки | `NotificationsService.createNotification` |

Отдельной библиотеки для APNs нет — запрос подписывается стандартным
`crypto` и уходит по `node:http2`. Единственное неочевидное место:
`crypto.sign` вызывается с `dsaEncoding: 'ieee-p1363'`, иначе Node отдаёт
подпись в DER, и Apple её отвергает.
