# Смена ключей и секретов

**Состояние на 06.09.2026:** JWT-секреты заменены, переменные Google убраны
с сервера, ключ Яндекс Облака ждёт замены, GitHub-токен проверен — утечки
нет (см. п. 3).

Порядок сверху вниз: сначала то, что действительно утекало, потом
гигиена перед релизом. Всё, кроме GitHub-токена, живёт в одном файле на
сервере — `/home/ubuntu/event_app_new/server/.env`.

Общая механика для любой серверной переменной:

```bash
ssh -i ~/.ssh/yandex-cloud ubuntu@213.165.213.224
```
```bash
cp /home/ubuntu/event_app_new/server/.env /home/ubuntu/backups/.env.$(date +%Y%m%d-%H%M%S)
nano /home/ubuntu/event_app_new/server/.env
pm2 restart event-app-server && pm2 logs event-app-server --lines 40 --nostream
```

Копия `.env` перед правкой — не формальность: файл на сервере и файл в
репозитории разные, восстановить его из git нельзя.

## 1. Google OAuth — ✅ отключён 06.09.2026, остался один шаг в консоли

**Что случилось.** В коммите «Working state from the old MacBook» в
`docs/GOOGLE_OAUTH_SETUP.md` лежали живые Client ID и Client Secret.
На GitHub они **не попали** — push-protection отклонил отправку, и вся
локальная история была схлопнута в один коммит с вычищенным файлом.
Но значение существовало в открытом виде, поэтому ключ считается
скомпрометированным.

**Что сделано.** Раз вход через Google выключен флагом
(`SHOW_GOOGLE_AUTH = false` в `client/app/(auth)/login.tsx`) и в ближайшее
время не вернётся, секрет решили не менять, а убрать совсем:
`GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` удалены из серверного `.env`
06.09.2026. Это безопасно — в `config/validation.ts` обе переменные
`optional()`, а `AuthService` создаёт OAuth-клиент только под
`if (clientId)`. Сервер перезапущен, API отвечает.

**Что осталось сделать руками:** https://console.cloud.google.com →
**APIs & Services → Credentials** → OAuth 2.0 Client ID проекта →
**Delete**. Тогда утёкший секрет перестанет существовать, а не будет просто
лежать неиспользованным. Когда вход через Google понадобится снова —
создаётся новый клиент, это несколько минут.

**Ещё одно место.** Локально сохранён тег `rollback-2026-08-14-root` — в нём
лежит та самая старая история со старым секретом. Его нельзя никуда пушить.
Когда убедитесь, что откатываться не придётся, удалите:

```bash
git tag -d rollback-2026-08-14-root
```

## 2. Yandex Cloud (почта Postbox) — обязательно

Через этот ключ уходят письма с кодами подтверждения. Переменные:
`YANDEX_CLOUD_ACCESS_KEY_ID`, `YANDEX_CLOUD_SECRET_ACCESS_KEY`.

1. https://console.cloud.yandex.ru → каталог проекта → **Сервисные
   аккаунты** → тот, от имени которого работает Postbox.
2. **Создать новый статический ключ доступа**, скопировать оба значения.
3. Вписать в `.env`, перезапустить сервер.
4. **Проверить, что письма ходят, и только потом удалять старый ключ.**

Проверка — зарегистрировать тестовый аккаунт в приложении и посмотреть, что
код пришёл. Если письма перестали ходить, в логе будет `identity not
verified` или ошибка авторизации:

```bash
pm2 logs event-app-server --lines 100 --nostream | grep -i -E "mail|postbox|identity"
```

Важно: регистрация **не падает**, когда письмо не ушло — аккаунт и код
создаются в любом случае. То есть сломанная почта со стороны пользователя
выглядит просто как «код не приходит», без единой ошибки на экране.

## 3. GitHub — персональный токен: утечки нет, менять не обязательно

**Проверено 06.09.2026.** Токена нет ни в рабочем дереве обоих репозиториев,
ни в одном коммите (включая тег `rollback-2026-08-14-root` со старой
историей, где лежит секрет Google), ни в `~/.git-credentials`, ни в
`~/.netrc`; в адресах `origin` учётные данные не зашиты. Токен живёт только
в связке ключей macOS. В список на замену он попал заодно с секретом
Google — оснований для этого не нашлось.

Так что ниже — обычная гигиена (полезно раз в несколько месяцев и при
смене машины), а не срочная задача.

Токен хранится не на сервере, а на вашем компьютере (в связке ключей
macOS / в git credential helper).

1. https://github.com/settings/tokens → у старого токена **Delete**.
2. **Generate new token** → права: `repo` (этого достаточно).
3. Первый же `git push` спросит логин и пароль — в поле пароля вставить
   новый токен, он сохранится в связке ключей.

Проверка:

```bash
git ls-remote origin > /dev/null && echo "доступ есть"
```

## 4. JWT-секреты — ✅ заменены 06.09.2026

`JWT_ACCESS_SECRET` и `JWT_REFRESH_SECRET` подписывают токены сессий.
Утечки не было, но менять их до прихода живых пользователей дешевле, чем
после: смена разлогинивает всех на всех устройствах разом.

Заменены на два новых случайных значения по 48 байт, сервер перезапущен.
Проверено: старый токен доступа получает 401, свежий вход — 201, запрос с
новым токеном — 200. Копия прежнего `.env` —
`/home/ubuntu/backups/.env.20260906-124956`.

Если понадобится повторить:

```bash
openssl rand -base64 48
```

Два **разных** значения в `.env`, `pm2 restart event-app-server`, заново
войти в приложении.

## 5. MinIO (хранилище картинок) — по желанию

Логин и пароль лежат сразу в трёх местах и должны совпадать:

- `/home/ubuntu/minio-ecosystem.config.js` — `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`
- `/home/ubuntu/start-minio.sh` — те же две переменные
- `server/.env` — `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY`

Менять все три сразу, потом перезапустить оба процесса:

```bash
pm2 restart minio && pm2 restart event-app-server
```

Проверка — загрузить фото в событие из приложения. Уже загруженные картинки
доступны на чтение и без ключей, поэтому «старые фото открываются» ещё не
значит, что всё хорошо: проверять надо именно загрузку.

## 6. Что трогать не нужно

- **`SMTP_*` и `SENDGRID_FROM_EMAIL`** — в коде сервера не используются
  вообще (почта идёт через Postbox). Мёртвые строки, можно просто удалить
  из `.env`.
- **`VK_*`** — VK mini app к iOS-релизу отношения не имеет. Если сервис не
  используется, токены проще отозвать в кабинете VK, чем менять.
- **Пароль базы в `DATABASE_URL`** — база слушает только localhost, снаружи
  недоступна, менять пароль ради релиза смысла нет.

## Проверка, что нигде больше ничего не лежит

Перед отгрузкой полезно ещё раз прогнать поиск по всему дереву:

```bash
git grep -nIE '(AKIA[0-9A-Z]{16}|AIza[0-9A-Za-z_-]{35}|GOCSPX-|ghp_[0-9A-Za-z]{36}|xox[baprs]-|sk_live_|BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY)' HEAD -- .
```

В прошлый раз находились только очевидные заглушки в `docs/` и `scripts/`
(`user:password`, `YOUR_PASSWORD`, локальный `postgres:postgres@localhost`).
Если найдётся что-то похожее на настоящий ключ — его нужно и поменять, и
вычистить из истории.
